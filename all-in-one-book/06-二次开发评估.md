# 第六章：二次开发评估

---

## 6.1 架构优点

1. **DI 容器 + 魔术属性带来极低的耦合门槛**：所有类通过 `Base.__get()` 访问服务，无需手动构造函数注入。添加一个新的 Model 或 Service 只需在 ServiceProvider 中注册，即可在任何地方通过 `$this->myNewModel` 使用。

2. **事件驱动的自动化体系非常灵活**：51 个内置 Action + 可扩展的 Action 基类，让"当 X 发生时自动做 Y"的场景无需写代码即可配置。新增自定义 Action 只需继承 `Action\Base` 并实现 4 个方法。

3. **多数据库支持**：同时支持 SQLite（零配置）、MySQL 和 PostgreSQL，覆盖从个人使用到团队部署的不同场景。Schema 迁移机制保证各数据库版本一致。

4. **插件系统设计完善**：提供 Hook、事件监听、DI 注册、路由扩展、数据库迁移等完整的扩展机制，插件可以在不修改核心代码的情况下添加功能。

5. **代码结构清晰可预测**：Controller、Model、Action、Validator、Formatter 等各类代码有明确的存放位置和命名规范，新开发者容易找到对应文件。

---

## 6.2 架构缺点 / 技术债

1. **Model 层职责过重**：Model 同时承担了数据访问、业务逻辑和事件触发三重职责，缺少独立的 Service 层。随着业务增长，Model 会变得越来越臃肿，难以进行单元测试。

2. **魔术属性依赖缺乏编译时安全**：`Base.php` 中 211 个 `@property` 注解依赖 IDE 支持来提示，运行时拼写错误不会报异常，而是返回 `null`，可能导致难以追踪的 Bug。

3. **无 ORM，SQL 操作分散**：数据库操作使用自建的 PicoDb 查询构建器，没有实体映射。复杂查询散布在各个 Model 中，数据库结构变更时需要全局搜索修改。

4. **Schema 迁移机制简陋**：使用纯版本号递增的方式管理迁移（`version_1` → `version_139`），没有回滚能力，不支持生成迁移脚本，多数据库之间版本不同步（MySQL 139 vs PostgreSQL 117）。

5. **缺乏中间件的请求/响应抽象**：中间件链是自建的简单链式调用，没有遵循 PSR-15 标准，难以与现代 PHP 生态中的中间件库互操作。

## 6.3 扩展性评分表

| 扩展维度 | 评分 (1-5) | 说明 |
|----------|:----------:|------|
| **插件扩展** | ⭐⭐⭐⭐ (4) | Hook 系统 + 事件 + DI 注册 + 路由 + Schema 迁移，覆盖大部分扩展场景；但 Hook 扩展点的文档不完善，需要阅读模板源码 |
| **API 扩展** | ⭐⭐⭐ (3) | JSON-RPC 过程可通过插件注册新方法，但协议限制（非 RESTful）使得与现代前端/第三方集成不太便利 |
| **数据模型扩展** | ⭐⭐⭐⭐ (4) | `*_has_metadata` 表提供 Key-Value 扩展、插件可创建自定义表；但无 ORM 意味着新表需要手写所有 CRUD |
| **UI 扩展** | ⭐⭐ (2) | 原生 PHP 模板 + Hook 注入点，缺少组件化能力；前端技术栈陈旧（jQuery + 原生 JS） |

## 6.4 常见定制场景难度评估

### 新增任务字段

| 步骤 | 操作 | 难度 |
|------|------|------|
| 1 | 在 Schema 迁移中 `ALTER TABLE tasks ADD COLUMN` | 🟢 低 |
| 2 | 修改 `TaskCreationModel::prepare()` 和 `TaskModificationModel` | 🟡 中 |
| 3 | 修改 `TaskValidator` 添加校验规则 | 🟢 低 |
| 4 | 修改表单模板（非后端范畴） | 🟡 中 |
| **总体** | **需要修改 3-5 个文件，无需改架构** | **🟡 中等** |

> **替代方案**：使用 `task_has_metadata` 表存储自定义字段，完全不需要改核心代码，但查询性能和类型安全会降低。

### 新增 API 方法

| 步骤 | 操作 | 难度 |
|------|------|------|
| 1 | 在 `app/Api/Procedure/` 下新建 Procedure 类 | 🟢 低 |
| 2 | 在 `ApiProvider` 中注册 | 🟢 低 |
| 3 | 添加 Authorization 类（如需权限控制） | 🟡 中 |
| **总体** | **结构清晰，照着现有 Procedure 写即可** | **🟢 简单** |

### 修改权限体系

| 步骤 | 操作 | 难度 |
|------|------|------|
| 1 | 在 `Role.php` 中添加新角色常量 | 🟢 低 |
| 2 | 修改 `AccessMap` 中的角色映射 | 🟡 中 |
| 3 | 修改 `ProjectUserRoleModel` 支持新角色 | 🟡 中 |
| 4 | 确保所有 Middleware 和 Authorization 类正确处理 | 🔴 高 |
| **总体** | **权限分散在多层，修改需全面覆盖** | **🔴 困难** |

### 自定义通知渠道

| 步骤 | 操作 | 难度 |
|------|------|------|
| 1 | 实现 `NotificationInterface` | 🟢 低 |
| 2 | 在 ServiceProvider 中注册 | 🟢 低 |
| 3 | 在 `UserNotificationTypeModel` 中添加类型 | 🟡 中 |
| **总体** | **接口简单明确，参考 `MailNotification` 即可** | **🟢 简单** |

### 新增自动化动作

| 步骤 | 操作 | 难度 |
|------|------|------|
| 1 | 继承 `Action\Base`，实现 4 个抽象方法 | 🟢 低 |
| 2 | 在 `ActionProvider` 中注册 | 🟢 低 |
| **总体** | **扩展性最好的部分，设计清晰** | **🟢 简单** |

## 6.5 技术债务清单

| 技术债 | 影响 | 优先级 |
|--------|------|--------|
| PHP 原生模板，无组件化 | 前端维护困难，无法复用 | 中 |
| 自建路由/中间件，非 PSR 标准 | 与生态脱节，难以引入第三方中间件 | 低 |
| PicoDb 自建 Query Builder | 功能受限，缺少 ORM 特性 | 中 |
| 无 Service 层，Model 过重 | 业务逻辑和数据访问耦合 | 高 |
| Schema 版本多数据库不同步 | MySQL 139 vs PostgreSQL 117，功能可能不一致 | 高 |
| 前端依赖 jQuery + 原生 JS | 技术栈陈旧，现代化改造成本高 | 低（如仅关注后端） |
| Session 存储可选但默认 PHP | 多实例部署需手动配置数据库 Session | 低 |
